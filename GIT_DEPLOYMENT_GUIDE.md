# 🔐 Git & Deployment Guide

## Should You Push Native Platforms to GitHub?

**Short Answer: NO** ❌

**Why:** Native platforms (`ios/` and `android/`) are **generated** from your source code and should NOT be in version control.

---

## ✅ What SHOULD Be in Git

### Source Code & Configuration:
```
✅ src/                          # Your app source code
✅ public/                       # Static assets (icons, manifest)
✅ capacitor.config.ts           # Capacitor configuration
✅ next.config.mjs               # Next.js configuration
✅ package.json                  # Dependencies and scripts
✅ package-lock.json             # Locked dependency versions
✅ tsconfig.json                 # TypeScript configuration
✅ tailwind.config.js            # Tailwind configuration
✅ .gitignore                    # Git ignore rules
✅ README.md                     # Project documentation
✅ All documentation .md files   # Guides you created
```

### Why These Should Be in Git:
- **Collaboration:** Team members can clone and work
- **Version Control:** Track changes over time
- **Deployment:** CI/CD can build from source
- **Backup:** Code is safely stored remotely

---

## ❌ What Should NOT Be in Git

### 1. Native Platform Directories (Already Ignored):
```
❌ ios/                          # Generated by Capacitor
❌ android/                      # Generated by Capacitor
❌ out/                          # Next.js static export output
❌ .next/                        # Next.js build cache
❌ node_modules/                 # npm dependencies
```

**Why Not:**
- **Generated files:** Can be recreated from source
- **Large size:** Makes repo huge and slow
- **Platform-specific:** Different developers might use different OS
- **Regenerated often:** Creates unnecessary git noise

### 2. Signing Keys (CRITICAL - NEVER COMMIT):
```
❌ *.keystore                    # Android signing key
❌ *.jks                         # Android signing key
❌ android/key.properties        # Android signing passwords
❌ ios/App/App/GoogleService-Info.plist  # Firebase/Google keys
```

**Why Not:**
- **Security:** Anyone with access can sign apps as you
- **Irreplaceable:** If leaked, must revoke and create new app
- **Legal liability:** Compromised keys = security breach

### 3. Environment Files with Secrets:
```
❌ .env.local                    # Local environment variables
❌ .env.production.local         # Production secrets
❌ .env.development.local        # Development secrets
```

**Why Not:**
- **Contains secrets:** API keys, database passwords, etc.
- **Security risk:** Leaked credentials can be exploited
- **Different per environment:** Each developer/deployment has different values

## 🔧 How to Set Up for Deployment

### Step 1: Verify .gitignore

Your `.gitignore` is now properly configured. Verify:

```powershell
# Check what would be committed
git status

# If you see ios/, android/, or .keystore files, they should NOT be there!
```

### Step 2: Remove Accidentally Committed Files (If Any)

If you already committed sensitive files:

```powershell
# Remove from git but keep locally
git rm -r --cached ios
git rm -r --cached android
git rm -r --cached out
git rm --cached *.keystore
git rm --cached android/key.properties

# Commit the removal
git add .gitignore
git commit -m "Remove generated files and sensitive data from git"

# Force push (if already pushed to remote)
git push origin main --force
```

**⚠️ Warning:** If you committed signing keys, they're in git history. You should:
1. Create a NEW keystore (old one is compromised)
2. Use `git filter-branch` or BFG Repo-Cleaner to remove from history
3. Or create a fresh repository

### Step 3: Commit Your Changes

```powershell
# Add all changes
git add .

# Commit with a message
git commit -m "Add mobile app setup and documentation"

# Push to GitHub
git push origin main
```

## 🚀 Deployment Workflows

### Workflow 1: Manual Deployment (What You're Doing Now)

```
Local Development
    ↓
1. Write code
    ↓
2. Commit to git (source only)
    ↓
3. Push to GitHub
    ↓
4. Pull on deployment machine
    ↓
5. Run: npm install
    ↓
6. Run: npm run build:capacitor
    ↓
7. Run: npx cap add ios/android (first time only)
    ↓
8. Run: npx cap sync
    ↓
9. Build in Xcode/Android Studio
    ↓
10. Upload to App Stores
```

**Pros:** Simple, full control
**Cons:** Manual work for each release

### Workflow 2: CI/CD Deployment (Advanced)

Use GitHub Actions or other CI/CD:

```
Push to GitHub
    ↓
GitHub Actions automatically:
  - Runs tests
  - Builds web app → deploys to Vercel
  - Builds iOS app → uploads to TestFlight
  - Builds Android app → uploads to Play Console
```

**Pros:** Automated, consistent builds
**Cons:** Requires setup, costs for build minutes

## 🔐 Handling Secrets

### Method 1: Environment Variables (Recommended)

**In your local machine:**
Create `.env.local` (not in git):
```bash
MONGODB_URI=mongodb+srv://...
LIVEKIT_API_KEY=...
LIVEKIT_API_SECRET=...
```

**In Vercel/Netlify:**
Add environment variables in dashboard:
- Settings → Environment Variables
- Add each secret

**In CI/CD:**
Add as GitHub Secrets:
- Repository → Settings → Secrets → Actions
- Add each secret

### Method 2: Secret Management Services

For production, use:
- **AWS Secrets Manager**
- **HashiCorp Vault**
- **Azure Key Vault**
- **Google Secret Manager**

## 📱 Recreating Native Platforms

Anyone cloning your repo can recreate platforms:

```powershell
# Clone repository
git clone https://github.com/yourusername/oppositelab.git
cd oppositelab

# Install dependencies
npm install

# Build for Capacitor
npm run build:capacitor

# Add platforms (first time only)
npx cap add ios
npx cap add android

# Sync (subsequent times)
npx cap sync

# Now ios/ and android/ directories exist locally!
```

**This is why you don't need them in git.**

## 🚨 If You Accidentally Committed Secrets

### Immediate Actions:

1. **Stop!** Don't push if you haven't yet
2. **Reset commit:** `git reset HEAD~1`
3. **Fix .gitignore:** Add the file pattern
4. **Recommit:** Without the secrets

### If Already Pushed:

1. **Revoke compromised credentials immediately**
   - Change API keys
   - Regenerate keystore (if exposed)
   - Update database passwords

2. **Remove from git history:**
   ```powershell
   # Remove specific file from all history
   git filter-branch --force --index-filter \
     "git rm --cached --ignore-unmatch path/to/secret/file" \
     --prune-empty --tag-name-filter cat -- --all
   
   # Force push
   git push origin --force --all
   ```

3. **Or use BFG Repo-Cleaner (easier):**
   ```powershell
   # Download BFG from: https://rtyley.github.io/bfg-repo-cleaner/
   
   # Remove file
   java -jar bfg.jar --delete-files secret-file.keystore
   
   # Clean up
   git reflog expire --expire=now --all
   git gc --prune=now --aggressive
   
   # Force push
   git push origin --force --all
   ```

4. **Consider creating fresh repository:**
   If keystore was exposed, safest is starting fresh

**Answer to your question:**
